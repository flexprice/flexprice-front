# Dark-mode audit — what still needs doing

Generated by walking the running app in dark mode with a contrast scanner, plus a static severity
sweep over the source. Re-run either at any time; both are described at the bottom.

## Headline

The dark theme is structurally sound. **No token is mis-designed** — every remaining defect is a
component still using a raw palette class, so the fix is to keep migrating, not to re-tune the
palette. Two exceptions were found and are already fixed (see _Token fixes_).

## Token fixes already applied

### `lib/typography.ts` — the single highest-leverage file

Every heading, label, body, table-header and breadcrumb style in the app resolves through
`getTypographyClass()`, and all 26 colour classes in it were hardcoded `text-zinc-*`. That is why
page headings rendered dark-on-dark at **1.18:1**. One file, 26 replacements, and every heading in
the product became readable. Home went from 7 contrast failures to 4.

### Four content tokens failed AA in dark

Measured every content token against the three common dark surfaces (`surface` #1d1d1f,
`surface-shell` #0f0f10, `surface-subtle` #232326):

| Token                  | Was       | Now       | Worst ratio before → after       |
| ---------------------- | --------- | --------- | -------------------------------- |
| `content-subtle`       | `#6e727b` | `#878c95` | 3.25 → 4.70                      |
| `content-zinc-subtle`  | `#6e727b` | `#878c95` | 3.25 → 4.70                      |
| `content-slate-subtle` | `#74787f` | `#858b96` | 3.53 → 4.63                      |
| `content-disabled`     | `#55585f` | unchanged | 2.20 — **left alone on purpose** |

`content-disabled` is meant to read as disabled, and WCAG exempts disabled controls. Brightening it
would make disabled fields look enabled.

**19 of 20 content tokens now clear AA in dark.** These were dark-only edits; light is byte-identical
and `verify:light` confirms it.

### `surface-inverse-zinc` added

`RevenueTrendCard`'s tooltip was `bg-zinc-900 text-white`. The text migrated to `content-inverse`
(which flips to near-black in dark) but `bg-zinc-900` had no bg-role token, so it stayed dark — dark
text on a dark tooltip. `surface-inverse-zinc` (zinc.900 → `#eeeff1`) inverts together with
`content-inverse`, the same pairing already used for the gray-based tooltips.

This is the third instance of the same trap (switch thumb, nightOwl code surface, now this): **the
question is never "what hex is this", it is "what does this sit on, and does that change".**

## Known non-issues

Things that look broken but are not:

- **Active sidebar item has no background in light.** shadcn's `data-[active=true]:bg-sidebar-accent`
  outranks the item's own class and resolves to an undefined variable in light. Pre-existing on
  `main`; only the border shows. In dark it correctly picks up the Midnight value.
- **Sidebar promo card missing.** Renders only when the environment has no plans and no features.
- **Light chips are below AA** (3.95–4.48). Pre-existing design, reproduced byte-for-byte. Fixing it
  is a visible light change and needs its own PR.

## Re-running the audits

```bash
npm run verify:theme          # token light values match their Tailwind sources
npm run verify:light          # every class mapped to the RIGHT token
npm run verify:tokens-staged  # index.css and tailwind.config.js committed together
```

For the in-browser contrast scan, open the app in dark mode and paste the scanner from this
workstream's session notes — it walks every text node, resolves the first opaque ancestor
background, and reports anything under 4.5:1 (3:1 for large text), grouped by class.
